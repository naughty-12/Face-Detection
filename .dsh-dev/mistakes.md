# 失误记录

> 记录**助手在工作中犯下的错误**：错在哪、影响多大、怎么发现、怎么修的、还留下什么。
> 与 `decisions.md`（主动做的决策）分工不同 —— 这里记的是**本可以避免的问题**。
> 新条目追加在最上方。判断标准：只写有证据的，不写"感觉不太对"。
>
> **为什么值得单独记**：这个项目最值钱的特性是"每个数字都标口径、未完成如实列出"。
> 一旦自己的表述开始脱离实测，这个特性就没了 —— 所以对失误也要用同一套标准留痕。

## 2026-09-22 失误 9：把"当时的权衡"写成"原则"，并把未根治项标成 ✅ 已完成

| 项 | 内容 |
|:---|:---|
| **错在哪** | ① 在 `docs/皮套联调问题与解决.md` 1.1 的状态行写下"**✅ 已完成**（未改动任何已安装的包 —— 环境当前验证可用，**重装会把它变成未验证**）"；② 同一说法还出现在 `CHANGELOG.md` 与 `docs/AI协作复盘.md` 8.1，共 **3 处**；③ 我还在对话里把它当成"值得讲的取舍"复述了一遍。 |
| **后果** | ① **这条理由逻辑上不成立**：验证是**可重复的动作**、不是一次性资产 —— 护栏 3 个用例 **0.1 s** 就能重跑，"会变成未验证"只描述一个几秒即可恢复的暂时状态，**不构成反对重装的理由**；② 它实际用的判据（"**现在没坏**"）正是本项目已明文否决的那一类（"能不能跑"不是环境正确的证据）；③ **把一个未根治的脆弱性标成了"✅ 已完成"** —— 冲突结构仍在（三个包都装着、生效者由安装顺序决定），根治路径从未做过，等于关掉了一个仍然开着的项。 |
| **怎么发现的** | 使用者在复核时直接指出"**有点过于牵强**"（2026-09-22）；随后全仓库搜"重装"发现同一说法共 **3 处**。**是被使用者指出来的，不是自查出来的。** |
| **根因** | 写状态时**没有区分"处置已完成"与"问题已根治"**；并且把"不想动一个已验证的环境"这个**权衡**包装成了**原则**（"会变成未验证"听起来正当，因此逃过了自查）。与失误 8 同族：**给一个未经检验的论断套上听起来正当的外壳** —— 不是编造数字，而是让表述强于证据。 |
| **修复** | ① 三处文字全部订正（联调文档 1.1 状态行 / `CHANGELOG.md` / `docs/AI协作复盘.md` 8.1）；② 未重装的理由改为**可核对**的两条：**收益为零**（重装不改变冲突结构）+ **风险非零**（安装顺序不受控；受限 shell 的 pip 会再生成一份用户目录副本 = 第四份）；③ 状态行改为"**处置已完成 + ⚠️ 未根治**"，并写明根治路径；④ `decisions.md` 新增一条记"**根治路径：把只用于可视化与一次已否决实验的第三方增强库从运行环境拆出 —— 未做**"。 |
| **要记住的** | ① 写状态**必须区分"处置已完成"与"问题已根治"**：未根治项一律带 ⚠️，不得只写 ✅。② **理由要写成可核对的收益 / 风险**，不能写成"别动没坏的东西"——后者是本项目已否决的判据。③ 自检一句话：**如果这条理由换到别的场景也照样说得通，它大概率不是理由，而是措辞。** |

## 2026-09-16 失误 8：第 5 条验收的"证据"只有文档里的数字 —— 采样脚本没入库、原始数据没落盘，且脚本结论行的判据是错的

| 项 | 内容 |
|:---|:---|
| **错在哪** | ① 那次 7 分钟稳定性采样用的是**临时脚本**：跑完就没了，仓库里**没有任何能产出这批数字的脚本**，原始采样数据也没落盘 —— 但文档已经把第 7 条（留证据）的证据改写成"**数字证据包**（采样记录 + VTS 日志 + 127 个测试）"，而这三样里其实只有"文档正文里抄下来的几个数字"加 VTS 日志。② 那个脚本的**结论行判据本身就是错的**：它把"桥接还没启动"（`connectedPlugins == 1`，只有采样器自己）的窗口算成掉线，于是打印"**未达 5 分钟或出现掉线，需重测**"——**与同一次运行的原始数据相反**。 |
| **后果** | 结论行与数据矛盾 → 这一条验收实际上**没有被判据支持**，只能靠人工核对原始数据改判（判据等于没起作用）；证据**不可复现**：别人拿不到脚本、也拿不到原始 CSV，无法自己重算那 10/10 个窗口。而第 5 条正是简历上"可长时间稳定运行"这句话的唯一支撑。 |
| **怎么发现的** | 2026-09-16 复核文档一致性时顺手做了一次证据溯源：全仓库搜 `connectedPlugins` **只命中文档正文**，没有任何脚本；仓库、桌面、下载、`Documents`、`%TEMP%` 都搜不到那次采样的原始文件；`artifacts/diag/` 里只有摄像头探针报告与截图。 |
| **根因** | 又是"**先给结论、后补证据**"的变体（与失误 2、3 同源）：把"脚本跑过了、屏幕上出现过数字"当成了"证据已经留下"。而**判据写错**的根因更具体 —— **没有先确认 `connectedPlugins` 这个字段的语义就把条件写进了脚本**（当时是"看着像会话数"）。 |
| **修复** | ① **先实测语义再写判据**：用 1 个 / 2 个探针同时连接，实测 `2 探针+桥接 = 3`、`1 探针+桥接 = 2`、`只有采样器 = 1`，并确认该字段来自 `StatisticsRequest`（同响应里 `allowedPlugins` 恒 = 1）；② 工具入库：`apps/vtube_bridge/sample_vts_params.py`（判据只从"连上那一刻"算起、原始 CSV 落盘、23 个单测覆盖判据与那个 bug）；③ 用该工具**重跑**：先是一次"人不在镜头前"的 10 分钟跑（判 FAIL，连接侧零掉线——**正好证明只看日志会误判**），
再是**人入镜**的 10 分钟跑，判 **PASS**：连续 599.7 s、19/19 窗口有动作、异常计数全 0，原始数据
`artifacts/diag/vts_stability_20260916-150813.{csv,json,txt}`（2090 行，独立重算复核一致）。 |
| **要记住的** | ① **能产出某个数字的脚本必须进仓库，那个数字才算证据**；"屏幕上出现过"不算。② **写判据之前，先把判据里每个字段的语义实测出来** —— 这次只花了一个 `StatisticsRequest` 就够，却省掉了整条验收的可信度问题。③ 判据的**结论行要跟原始数据一起落盘**，否则"结论与数据矛盾"这种错只能靠人工发现。 |

## 2026-09-16 失误 6：又一次给出没验证的"可执行步骤" —— "拖 .model3.json" 被 VTS 直接拦掉

|:---|:---|
| **错在哪** | 发现"hiyori 被加载成挂件"之后，我给出的修复第一步是"**拖 `hiyori.model3.json` 这个文件**进 VTS 窗口"，并把它写进了 `apps/vtube_bridge/README.md` 的第 2、3 步。用户照做，**被 VTS 当场拦截**。 |

Drag & drop is disabled for this type.`（用户 12:56:08 与 12:58:26 各试一次），启动时加载的设置也写着 `Blocked file types: ".pdf", ".txt", ".html", ".json"`。而**唯一被允许拖放的"模型相关"类型是文件夹**，文件夹必定走 `Live2D Item` 路径（`Dragged folder is a Live2D Item`）—— 所以**"拖放"这条路根本不可能加载出主模型**。 |

## 2026-09-16 失误 4：把"查不到"当成了"不存在" —— 我断言本机没有摄像头

| 项 | 内容 |
|:---|:---|
| **错在哪** | 用 `Get-PnpDevice -Class Camera` / `-Class Image` 查询返回空，就直接给出结论"**本机没有摄像头**"，并据此建议改用视频文件跑链路。 |
| **事实** | 本机**有**内置摄像头：`USB\VID_0C45&PID_6A14&MI_00` = **Integrated Webcam**，类别 Camera，`Status: Started`；系统隐私使用记录还显示**同一个 `python.exe`（同一解释器路径）在 2026-07-30 成功使用过它**。用户在自己终端实测 `cv2.VideoCapture(0)`（默认 MSMF）与 `cv2.CAP_DSHOW` **都返回 `opened True`**。 |
| **怎么发现的** | 用户回复"**一定要本机的摄像头我的考虑**"，我才换路径重查：`pnputil /enum-devices /connected` 直接列出了该设备，注册表 `DeviceClasses\{e5323777-…}`（VideoCapture 接口类）也能查到。**是被用户推回来的，不是自己发现的。** |
| **为什么没自查到** | 漏看了**查询本身失败**的信号。同一批命令里已经出现两个警报：`Get-PnpDevice` 返回的**设备总数是 0**（任何真实 Windows 机器都不可能是 0），`Get-CimInstance Win32_ComputerSystem` 返回"**拒绝访问**"。这两条都在喊"是查询被挡了"，而我把空结果读成了否定答案。 |
| **影响** | 给出了与事实相反的环境结论。若用户照此放弃摄像头路线，"摄像头驱动皮套"这个核心目标会被错误地判为不可行 —— 而它其实完全可行。 |
| **修复** | ① 改用**互相独立**的取证路径：`pnputil`、注册表 `DeviceClasses` / `Enum\USB`、系统隐私使用记录、以及多后端 × 多 index 的实测；② 结论订正为"设备存在且 Started，但**受限 shell 拿不到设备**，用户自己的会话可以"（已由用户终端的两条实测确认）；③ 与实测证据一起写入 `MEMORY.md`。 |
| **要记住的** | **空结果不是否定证据 —— 先证明"这次查询本身有效"**。可操作的判据：如果一次枚举返回的数字在物理上不可能（设备数 = 0），那说明的是工具或权限，而不是机器。<br>配套的近失误：同一次排查里我还说过"`websockets` 没装"，实际是**查错了包名** —— 桥接用的是 `websocket-client`（提供 `websocket` 模块），依赖本来就是齐的。同一类毛病的两种表现：**把一次未经验证的查询当成了结论。** |

## 2026-09-15 失误 3：先给结论、后测量 —— 把猜测写进了文档

| 项 | 内容 |
|:---|:---|
| **错在哪** | 端到端实测发现"240 帧视频只发出 120 帧（20 帧/秒）"后，我**在没有加计数器的情况下**直接给出解释 —— "发送线程与主循环争 GIL" —— 并把这个结论写进了 `apps/vmc_link/README.md`、`apps/unity_link/README.md`、三线方案与 CHANGELOG。 |
| **事实** | 加上计数器后实测：**管线本身跑到 40.1 帧/秒**，跟 GIL 毫无关系。真正原因是**限频判据与帧间隔的整除关系** —— 管线帧间隔 24.9 ms 小于限频门限 33.3 ms（1/30），导致"每帧都差一点点、隔帧才发一次"，于是 240 帧只发出 120 帧。 |
| **怎么发现的** | 基于错误假设做的第一版修复（把发送线程改为主循环内联发送）**没有提升速率**（120 → 120 帧）。这次改动的失败让我不得不加 `frames_sent` / `frames_skipped` / `管线帧率` 三个计数器，才看到真实分布。**是"修复无效"逼出来的测量，不是主动测量的。** |
| **影响** | 文档里出现了一段错误的机制解释，且**第一版修复完全打偏**（改的是线程模型，问题在限频判据）。如果没做第二次测量，这段错误解释会被用户当成事实引用。 |
| **修复** | ① 移除两个 UDP 出口的速率上限（无背压的数据报，限频只有害处）：**发送 240 帧 / 240 帧，40.2 帧/秒**，皮套更新率翻倍；② `--send-fps` 明确为"仅 VTS 出口生效"；③ 三处文档的"GIL 争用 / 21.4 帧/秒"表述全部订正为实测原因与数字；④ 桥接主循环结束时**新增 summary 打印**（处理帧数、管线帧率、各出口发送数），让下次不必再靠猜。 |
| **要记住的** | **有计数器就不要靠推理**。这类"慢了/少了"的问题，第一步是**测出分布**（处理多少帧、发出去多少、各阶段耗时），而不是先构造机制解释。本次若一开始就加计数器，能省掉一次无效修复和四处文档订正。<br>更一般的规则：**把机制解释写进文档的资格，与它是否有实测支撑是同一件事** —— 这与 `conventions.md` 里"对外表述只能按实际达到的层次写"是同一条原则。 |

## 2026-09-15 失误 1：给出的可执行步骤，实际跑不起来（GUI 硬依赖未验证）

| 项 | 内容 |
|:---|:---|
| **错在哪** | 在 `docs/plans/2026-09-15-皮套Unity落地.md`（**该文件后已更名为「皮套落地三线」**）与 `apps/unity_link/README.md` 里，把 `python apps/vtube_bridge/main.py --input 0 --sink unity` 写成 P0 的第一步命令，**但从未验证它能不能启动**。 |
| **事实** | `run_bridge()` 里有硬依赖：`if QtWidgets is None: raise RuntimeError("PyQt5 is not available.")` —— 只要没装 PyQt5，**连摄像头都不会打开**。实测本机：`python -c "import PyQt5"` → `ModuleNotFoundError: No module named 'PyQt5'`。`requirements.txt` 第 8 行虽声明 `PyQt5>=5.15.0`，但**未安装**。 |
| **怎么发现的** | 用户指出"我的摄像头一直不是 Qt 做界面的"，顺着这条线去查环境，才看到 PyQt5 根本不存在。**是被用户发现的，不是自己发现的。** |
| **影响** | 用户按步骤执行必然失败，且失败点（缺 GUI 依赖）与要验证的目标（UDP 参数流）毫无关系，容易误导排查方向。 |
| **为什么没自查到** | 本次只验证了 `selfcheck.py`（走的是直接实例化 `UnityUdpSink` 的旁路）与 `--help`（能看到参数就以为命令可用）。**"参数存在" ≠ "命令能跑"** —— 没有执行主程序本身。 |
| **修复** | 新增 `--no-gui`：无窗口模式下用 `HeadlessDebugWindow` / `_HeadlessApp` 顶替 Qt 窗口，**不装 PyQt5 也能跑 `--sink unity` 或 `--sink vts`**；缺 PyQt5 且未加 `--no-gui` 时，报错信息直接指向该开关。已静态核对 `run_bridge` 用到的 8 个窗口接口（`closed`/`target_center`/`camera_preview_enabled`/`show`/`close`/`update_frame`/`update_tracking_snapshot`/`processEvents`）全部由替身覆盖。 |
| **仍残留** | 无窗口路径**未用真实摄像头实跑过**（本机不具备条件），只做了语法、参数暴露与接口覆盖三项静态验证。 |
| **要记住的** | 交付"可执行步骤"时，必须至少把**主程序本身**跑一次到"能进入主循环"为止；只验证它依赖的某个函数是不够的。 |

## 2026-09-15 失误 2：把从未运行过的功能写进了简历稿

| 项 | 内容 |
|:---|:---|
| **错在哪** | `docs/简历项目经历.md` 的可粘贴版本里，把"**PyQt5 实现 16 参数实时监视面板、点击选脸、一键回中、范围自动采集**"写成已完成能力，并列入技术栈（3.1 / 3.2 / 3.4 三处）。 |

| **要记住的** | 审核任何对外表述（简历、README、答辩稿）时，判据不是"仓库里有没有这个文件"，而是"**有没有运行记录 / 日志 / 截图**"。建议做法：每条表述后面在心里问一句"证据在哪一层"——源码层、运行层、还是只有设计层。 |

## 附：这两个失误的共同根因

**把"仓库里存在"当成了"已经验证"。**

本项目的文档体系一直强调"口径"与"未实测不写"，而这两次失误恰恰违反了它 ——
只不过违反的方式很隐蔽：不是编造数字，而是**默认了"有代码 = 能用"**。
可用的自查动作只有一个：**对每条对外表述追问它属于哪一层**（设计 / 源码 / 运行 / 有日志与截图），
并且**只按那一层的强度去写**。
