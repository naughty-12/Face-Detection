## 2026-09-22 三个 OpenCV 分发包共用 `cv2/`：**处置已完成，问题未根治**（含根治路径，未做）

### 背景

`opencv-python` / `opencv-python-headless` / `opencv-contrib-python` 是三个**不同发行包**，
却都往同一个 `site-packages/cv2/` 装文件 → **最后安装者生效**。实测三者分别由
**ultralytics**（`opencv-python>=4.6.0`）、**mediapipe**（`opencv-contrib-python`）、
**albumentations**（`opencv-python-headless>=4.9.0.80`）拖入 —— **没有一个是为"用 OpenCV"单独装的**。
记录状态原文是"**隐患，尚未爆**"；处置（声明收敛 + 护栏测试）此前已完成，但被标成了 ✅ —— 
该标记与理由口径已于 2026-09-22 订正（见 [`mistakes.md` 失误 9](mistakes.md)）。

### 关键新事实（2026-09-22 复核，全部实测）

| 事实 | 证据 |
|:---|:---|
| 冲突结构**无法用声明消除** | 依赖解析只看"包名 + 版本"，**不判断目录归属**；三方从元数据看都满足，`pip check` 无异常 |
| 元数据与实物不符 | `pip show opencv-python` 报 **4.13.0.92**，`cv2.__version__` 报 **5.0.0** |
| 当前生效的是 **contrib** 构建 | `cv2.face` / `ximgproc` / `aruco` 存在；五个 GUI 符号（`imshow` / `waitKey` / `destroyAllWindows` / `getWindowProperty` / `WND_PROP_VISIBLE`）实测全部存在 |
| 护栏**当前为绿** | `tests/test_opencv_environment.py` **3 个用例全过**（含 2 个反向用例：构造无 GUI / 部分缺失的假构建，验证它真能红） |

### 候选方案

| 方案 | 内容 | 取舍 |
|:---|:---|:---|
| A | **重装 contrib**，让它成为最后安装者 | ❌ 否决：**收益为零**（不改变"三个包都装着、顺序决定生效者"的结构）+ **风险非零**（顺序不受控；受限 shell 的 pip 会再生成一份用户目录副本 = 第四份） |
| B | 用依赖约束 / 锁文件把三个包收敛 | ⚠️ 受限：albumentations **硬依赖 headless**，除非换库或不装它 |
| **C（已落地）** | 声明只留必需的一个（contrib）+ 根因注释 + **护栏测试**（缺 GUI 符号即失败、不 skip） | 仍是**缓解**：让冲突**可见**，不消除冲突 |
| **D（根治，未做）** | 把只用于**可视化 + 一次已否决实验**的第三方增强库从**运行环境**拆出 | 最干净的一条 —— 它本就不参与产品运行；代价是会影响那次实验的可复现性 |

### 结果与残留

- **已完成**：`requirements.txt` 声明收敛 + 根因注释；`tests/test_opencv_environment.py`（3 用例，含反向用例）；
  三处"重装会把它变成未验证"的理由口径订正（`CHANGELOG.md`、`docs/皮套联调问题与解决.md` 1.1、`docs/AI协作复盘.md` 8.1）。
- ⚠️ **未根治**：headless 一旦成为最后安装者，上述五个符号消失 → 实时预览崩，
  且**报错指向 `cv2.imshow`、不提安装顺序**（排查方向被带向代码）。**D 方案未做。**

## 2026-09-16 第 5 条稳定性判据：**先实测 `connectedPlugins` 语义，再把采样器入库**

### 背景

线 A 验收第 5 条（连续 ≥5 分钟稳定）此前**判通过**（10/10 个 30 s 窗口、无掉线、≈5.0 分钟），
但复核时发现两处欠账（详见 [`mistakes.md` 失误 8](mistakes.md)）：那次采样是**临时脚本**跑的
（**脚本没进仓库、原始数据没落盘**），而**脚本结论行的判据本身是错的** —— 它把"桥接还没启动"
（`connectedPlugins == 1`）算成掉线，结论与自己的数据相反，靠人工核对才改判。

### 关键新事实（全部实测，2026-09-16）

| 事实 | 证据 |
|:---|:---|
| `connectedPlugins` 来自 **`StatisticsRequest`**，含义是**活着的 API 会话数（含采样器自己）** | 桥接在线时：2 探针+桥接 = **3**、1 探针+桥接 = **2**；同响应 `allowedPlugins` 恒 = 1 |
| **`plugins == 1` = 桥接还没起来，不是掉线** | 同上；也解释了旧脚本为什么误报 |
| 读参数用 `ParameterValueRequest`，键名是 **`name`**，且**一次只返回一个参数** | 传 `id` → `APIError 500 "You have to provide a parameter name."`；传 `name` → `ParameterValueResponse` |
| 采样器复用桥接的插件身份 + 缓存 token，**不会二次弹授权窗** | 实测连接即 `authenticated: true`；VTS 日志只有一条 `Plugin "Face Detection VTube Studio Bridge"` 身份 |

### 候选方案

| 方案 | 内容 | 取舍 |
|:---|:---|:---|
| A | **不补**：沿用文档里那批数字 | ❌ 否决：不可复现、无法被别人重算，而这是"简历上写稳定运行"的唯一支撑 |
| B | **人工记录**：每次跑完手工抄几个数字进文档 | ❌ 否决：判据不可执行 → 正是旧脚本"结论与数据矛盾却没人发现"的成因 |
| **C（选定）** | **采样器入库** + 原始数据落盘 + 判据写进测试 | 数字可复现；判据本身也有回归测试 |

### 选定方案的三个具体取舍

1. **默认采 600 s、要求 300 s**：留 5 分钟余量，避免又出现"≈5.0 分钟正好卡线"。
2. **`connectedPlugins >= 1 + 其它插件数` 才起算**，且连续时长取**最长的一段**（断线/采样中断重新计）
   —— 采样器自己占 1 个会话这一点必须写进判据，否则又会误判。
3. **原始 CSV 边采边写、每行 flush**：半路崩掉也留下已采数据（"跑完才落盘"正是丢掉证据的形态）。

### 结果与残留

- 新增 `apps/vtube_bridge/sample_vts_params.py` + `tests/test_vts_stability_sampler.py` **28 个**
  （其中一条专门钉"启动前的窗口不算掉线"）→ 全量 **155 / OK**；两个判据行为用**变异测试**验证过
  （把 gap 检查与错误分类改坏，对应测试立刻红）。
- **两次 10 分钟实跑构成对照**（这也是本条决策的价值证明）：**人不在镜头前**那次判 **FAIL（4/19）**
  —— 连接侧连续 599.9 s、掉线/采样失败/中断/VTS 重启全 0，但 **t≈102 s 起参数回落到 VTS 默认值**
  （`faceFound:false`），后 480 s 全 BAD；**人入镜**那次（15:08:13–15:18:13）判 **PASS** ——
  连续 **599.7 s**、**19/19** 窗口有参数在变化、异常计数全 0，原始数据
  `artifacts/diag/vts_stability_20260916-150813.{csv,json,txt}`（2090 行）**独立重算复核一致**。
  → **只看连接状态/VTS 日志会把前者误判成"稳定 10 分钟"**：判据必须包含"参数真的在动"。
- 顺带实测到"**离开画面再回来仍能跟随**"：15:03:34–15:03:54 采到 VTS 默认值（无人入镜），
  15:07:57 再采已恢复（`MouthOpen` 0.223→0.258、`FaceAngleX` −0.42→2.27）。
- **残留**：① "先采样后桥接"的**真实顺序**（启动初期 `plugins == 1` 不算掉线）目前只有单测覆盖，
  真机顺序验证待做；② 桥接**没有任何界面提示"当前没检出人脸"**，只能靠采样器的 CSV 事后发现
  （已由本次 FAIL→PASS 对照暴露出来）；③ 第 6 条（端到端延迟）仍无实测手段。

## 2026-09-16 皮套联调的问题修复策略：**逻辑错改代码，幅度/量程用校准**

### 背景

线 A（VTS + Live2D）首次真机联调，共发现 8 个问题（详见
[`docs/皮套联调问题与解决.md`](../docs/皮套联调问题与解决.md)）。其中性质并不相同，
若一律"改代码"或一律"用校准"，都会出错。

### 关键区分（为什么必须分流）

| 类型 | 判据 | 处理 |
|:---|:---|:---|
| **逻辑 bug** | 数值在**链路内部**被算错，可**确定性复现**（如 `0.97 -> 0.000`、方向被取反） | **改代码 + 回归测试** |
| **感知层幅度不足** | 链路**忠实传递**，但输入本身到不了量程（MediaPipe 的眨眼上限实测只有 ~0.75） | **用校准补偿**，不改代码 |
| **量程不匹配的固有损失** | 源范围与目标范围之比带来的固定折损（源 ±45° → VTS ±30° = 0.67 倍） | **用校准把源范围对齐目标范围** |

### 候选方案

| 方案 | 内容 | 取舍 |
|:---|:---|:---|
| A | **全部改代码**：给眨眼加增益常数、给角度乘固定系数 | ❌ 否决：把"与相机/距离/光线相关"的实测值写死进代码，换个人或换个距离就不对 |
| B | **全部用校准** | ❌ 否决：映射退化（`EyeOpenLeft` 恒 0）与视线取反是**逻辑错误**，校准只能掩盖，换个参数还会再犯 |
| **C（选定）** | **按类型分流**：逻辑错 → 代码 + 测试；幅度/量程 → 校准 JSON（可按条件重测） | 各自用在对的地方；校准带明确口径 |

### 结果与残留

- 4 个代码 bug（授权超时、映射退化、视线取反、OpenCV 护栏）**全部有回归测试**：
  新增 **22 个测试**，全量 **78 tests / OK**（原 56）。
- 3 处校准写在 `apps/vtube_bridge/config/tracking_calibration.json`
  （`EyeOpenLeft/Right`、`FaceAngleX/Y/Z`），**口径依赖当前相机 / 距离 / 光线**，换条件需重测。
- **残留（易用性缺口）**：`--no-gui` 下**没有 GUI 校准入口**（项目决定不装 PyQt5），
  校准只能手写 JSON —— 若线 A 要继续用，值得补一个"命令行采集校准"的小工具。

## 2026-09-16 OpenCV 分发包冲突：只改声明 + 加护栏，不统一版本

### 背景

排查"`pip show opencv-python` 报 4.13.0.92，而 `cv2.__version__` 报 5.0.0"时发现，本机同时装了
三个 OpenCV 分发包：`opencv-contrib-python 5.0.0.93`、`opencv-python 4.13.0.92`、
`opencv-python-headless 4.13.0.92`。

### 为什么会这样（根因，三层）

1. **三个包写的是同一个目录**：它们是三个不同的 PyPI 发行包，却都往
   `site-packages/cv2/` 里装文件，而 Python 只能 import 到一个 `cv2` ——
   所以**谁最后被安装，谁的构建生效**，先装的被逐文件覆盖。
2. **pip 不会把它们当成互斥**：包名不同，且分别被不同依赖要求 ——
   `mediapipe → opencv-contrib-python`、`albumentations → opencv-python-headless`、
   我们原先的 `opencv-python` —— pip 于是"忠实"地三个都装。**结果是三个 `.dist-info`
   都留在元数据里，而磁盘上只有一份 `cv2/`**，于是出现"版本号自相矛盾"的现象：
   `cv2.__version__` = 5.0.0（contrib 赢），`pip show opencv-python` = 4.13.0.92（看元数据）。
   **这不是缓存或路径问题，是同一个目录被三方共写。**
3. **危险只在"赢家是谁"**：`opencv-python-headless` 不带 GUI。一旦它成为最后安装者，
   项目调用的 `imshow` / `waitKey` / `destroyAllWindows` / `getWindowProperty` /
   `WND_PROP_VISIBLE` 全部消失，实时预览直接崩，而**报错会指向 `cv2.imshow`，
   不会提示"安装顺序"这个真正的原因**。

### 证据

| 检查 | 实测 |
|:---|:---|
| `cv2.__version__` | 5.0.0；且 `cv2.face` / `ximgproc` / `aruco` / `dnn_superres` 均存在 → 生效的是 **contrib** 构建 |
| `cv2.__file__` | `...\site-packages\cv2\__init__.py`（三者共用这一份） |
| `pip check` | No broken requirements（pip 自己不认为有问题） |
| 项目单测（改动前） | **Ran 56 tests / OK** —— 即：功能正常，问题是"脆弱"而非"已坏" |
| 摄像头 / ultralytics 导入 | 均正常 |

### 候选方案

| 方案 | 内容 | 取舍 |
|:---|:---|:---|
| **A（选定）** | 改 `requirements.txt` 声明 + 加护栏测试（TDD） | 零风险、不动已装包；把"随时会坏"变成"坏了立刻红" |
| B | 把三者统一到 4.13 线重装 | **不做**：当前环境已验证可用（56 测试 OK + 摄像头可用），重装会把它变成未验证；且 mediapipe 对 contrib 的版本约束尚未核实 |
| C | 只删 `opencv-contrib-python` | **不可行**：mediapipe 依赖它 |
| D | 只删 `opencv-python-headless` | **不可行**：albumentations 依赖它（删后 `pip check` 会破） |

### 决策

采取 A：

1. `requirements.txt` 的 OpenCV 行由 `opencv-python>=4.5.0` 改为 `opencv-contrib-python>=4.5.0`
   （mediapipe 真正要求的那一个），并加注释写明根因与"禁止 headless 收尾"。
2. 新增 `tests/test_opencv_environment.py`：断言当前 `cv2` 具备项目**实际调用**的 5 个 GUI 符号；
   缺符号时**失败而非 skip**（skip 掉的护栏等于没有护栏），失败信息直接给出修复命令。

### 结果与残留

- 按 TDD 落地：先写测试 → 实测 `NameError`（红，3 errors，Ran 59）→ 写最小实现 → **Ran 59 / OK**（绿）。
- **残留风险**：任何一次 `pip install`（例如升级 albumentations）都可能让 headless 重新成为
  最后安装者。护栏能拦住它，但**护栏只在跑测试时生效**。
- **操作红线（实测）**：受限 shell 里 pip 会退化为 user 安装（原文
  `Defaulting to user installation because normal site-packages is not writeable`），
  会**再装一份到用户目录，制造第四个副本** —— 因此 pip 必须在使用者自己的终端执行。

## 2026-09-15 皮套形态改定：2D Live2D 优先，VTS 路线重新启用为线 A

> **本条修正同日的两条决定**：① "皮套出口最终选定 Unity 单路线"；
> ② 三线条目里把速通线定为 VMC + VSeeFace（3D）。
> VTS 那条路此前记的是"不做"，现在**重新启用为线 A**，理由见下。

### 背景

用户在看过 3D 免费样本模型后明确反馈"**3D 的好像有点丑**"，要 2D 皮套。这否定了"先跑 3D"的前提。

### 关键新事实（核查 + 实测）

1. **VTS 出口是项目原有实现，代码零改动** —— `VTubeStudioWorker` / `VTubeStudioClient` 一直存在，
   而且我们的参数名（`FaceAngleX/Y/Z`、`MouthOpen`、`EyeOpenLeft/Right`、`EyeLeftX/Y`…）
   **本来就是按 VTube Studio 的标准定的**。
2. **"PyQt5 依赖"这条否定理由已经不成立**：`--no-gui` 让 VTS 出口可以无窗口运行。
   **实测**：本机**没有装 PyQt5**，`--sink vts --no-gui` 仍正常启动并尝试连接
   `ws://127.0.0.1:8001`（日志 `Connecting to VTube Studio ...` → `[WARN] VTube Studio unavailable: timed out`，
   因为 VTS 确实未安装，属预期）。
3. **Live2D 官方样本库可免费使用**，且下载包内含 **runtime folder**
   （`.model3.json` + `.moc3` + 纹理 + 物理设置）—— **正是 VTS 能直接导入的格式，不需要 Cubism Editor**。
   授权：个人 / 小规模企业（年销售额 < 1000 万日元）**可商用也可非商用**（Unity-chan 与初音未来除外），
   但**必须标注指定版权声明**，个别角色（Hiyori / Miara）**不得改动设计**。
4. **2D 比 3D 多一项能力**：VTS 有标准视线参数，而我们的管线本来就输出眼球方向；
   VMC/3D 那条路当前**不发**视线。

### 决策

1. **线 A（速通线）= VTube Studio + Live2D（2D）**，代码零改动。
2. **VMC + VSeeFace 降为 3D 备选**，代码与手册保留、不占线位（它证明"出口可替换"这条架构决策）。
3. **不装 PyQt5**，继续统一 `--no-gui`。
4. 待做：装 VTS → 开插件 API → 导入官方样本模型（推荐 Hiyori / Epsilon / Izumi / Zundamon）→
   关掉 VTS 自带追踪 → `--sink vts --no-gui` → 过 7 条验收 → 录视频。
   操作手册见 [`apps/vtube_bridge/README.md`](../apps/vtube_bridge/README.md)。

### 结果与残留

- 三线方案总览表、模型来源表、验收说明、衔接表已按本条更新。
- **仍未验证**：VTS 真机联调（连接 → 授权 → 参数注入 → 皮套跟随）。本机未安装 VTube Studio，
  已实测的只有"无 PyQt5 也能启动并尝试连接"。
- **授权注意**：用官方样本模型发布的任何内容（含演示视频）**必须带那段指定版权声明**；
  这不会影响 SDK 授权红线（我们没集成 Cubism SDK）。

| **B 目标线** | 自定义 UDP JSON | Unity + UniVRM / Live2D | 中 | 产出 **C#/Unity**（投客户端岗的硬缺口）；表现层自己掌控 |
| **C 保底线** | 不新增技术工作 | 沿用线 A 成果 | 0 | 线 B 卡住时，简历仍有可写内容 |

### 关键新事实（此前遗漏）

**VMC Protocol 是 VTuber 圈的事实标准，MIT 许可，OSC over UDP**，角色定义恰好套上本项目：
我们的工具就是标准的 **Assistant**（只发部分骨骼 + 面部表情给 Performer），
而规范约定 Assistant→Performer 走 **39540**。也就是说**不需要写任何引擎代码**，
只要按规范发 blendshape，就能驱动 VSeeFace 里现成的 VRM 皮套。

### 决策

1. 三条线并行记录，**删除此前所有类似方案**（VTS 桥接路线、Unity 单线计划）。
2. 桥接新增第三个出口 `--sink vmc`（`VmcOscSink`），`--sink` 改为支持逗号组合
   （`vmc,unity`；别名 `both`=vts+unity、`all`=全部），**任何既有出口行为不变**。
3. 实现范围严格按规范最小集：`/VMC/Ext/OK`、`/VMC/Ext/T`、`/VMC/Ext/Blend/Val`×N、
   可选 `/VMC/Ext/Bone/Pos`（头部）、`/VMC/Ext/Blend/Apply`。**不打包 bundle**（规范允许逐条发）。
4. 表情名默认用 **VRM0 预设**（`A`/`Joy`/`Blink_L`），因为规范要求 VRM1 发送端也必须按 VRM0 发以兼容旧应用；
   提供 `--vmc-vrm1-names` 切换。
5. **先验证关键假设再往下做**：VSeeFace 是否接受"只发头部+表情的 Assistant 数据"未经实测；
   有第三方工具佐证（VroidPoser、ThreeDPoseTracker→VSeeFace 实践），但需 10 分钟实测确认，
   不通则换 Warudo / VirtualMotionCapture。

### 结果

计划见 [`docs/plans/2026-09-15-皮套落地三线.md`](../docs/plans/2026-09-15-皮套落地三线.md)（取代已删除的 Unity 单线计划）；
线 A 操作手册见 [`apps/vmc_link/README.md`](../apps/vmc_link/README.md)；
线 B 操作手册见 [`apps/unity_link/README.md`](../apps/unity_link/README.md)。

**已自检**（不依赖摄像头/VSeeFace/Unity）：OSC 编码逐字节符合规范、取值方向正确
（睁眼 0.2 → `Blink_L` 0.8）、帧内 `Apply` 顺序正确、VRM0/VRM1 两套名可用、

## 2026-09-15 Albumentations 增强管线的定位（方案 B：不接入训练）

### 背景

`src/data/augment.py` 定义了 early/late 两套 Albumentations 增强管线，但**从未进入训练** ——
只被 `src/data/vis_aug.py` 引用。设计文档承诺的"后 50 epoch 加 Cutout/模糊"因此看起来没做。
G12 要回答：接入、删除，还是保持现状？

### 候选方案

| 方案 | 做法 | 评价 |
|:---|:---|:---|
| A. 删除 | 清掉"文档写了、代码没用"的落差 | 会失去现成的增强可视化工具 |
| **B. 保留但明确定位为可视化工具（选定）** | 文件头写清定位与原因，文档同步 | 零风险，且纠正文档落差 |
| C. 真正接入训练 | 自定义 Dataset + trainer 钩子 | 投入大、**当前收益为负** |

### 选定 B 的理由

**该管线的全部变换都已被 ultralytics 内置增强覆盖**：`HorizontalFlip`↔`fliplr`、
`RandomBrightnessContrast`/`HueSaturationValue`↔`hsv_v`/`hsv_h`/`hsv_s`、`Blur`↔`randaugment`
（含模糊）、`CoarseDropout`↔`erasing`、`Resize`↔letterbox。而且它**缺 Mosaic**（ultralytics 在
检测任务上最有价值的增强）。因此：

- **替换** ultralytics 的增强 → 丢掉 Mosaic，严格变差；
- **叠加** → 翻转与 HSV 被施加两次、概率失准。

顺带纠正一个认知：设计文档承诺的"后 50 epoch 加 Cutout/模糊"**其实早已被 ultralytics 的默认值满足**。

### C 若要做，重点是什么（已写入优化方向）

收益不在"多几种标准增强"，而在 ultralytics 做不到的两件事，各自对应一个**已实测的短板**：

1. **属性感知增强** —— 用 WIDER 标注自带的脸级属性（`blur` / `illumination` / `occlusion` / `pose`）
   做定向增强；ultralytics 看不到这些字段（G14）。依据：≥32px 人脸的召回已达 **0.916**，
   剩余失误集中在困难子集，而困难程度**标注里就有**。
2. **小脸放大裁剪** —— 随机裁出含小人脸的区域并放大到 640。依据：**72.5% 的 GT 人脸 <32px，
   其召回仅 0.493**。

真实成本（**后续查证已大幅下调**，见本节末"载体订正"）：① 若挂入的变换与内置重叠，需关闭内置
对应项以免双重施加（只挂不重叠的变换则无需）；~~② 自行实现 Mosaic~~ —— **不需要**，钩子运行在
Mosaic 之后；③ 打通 ultralytics 的 Dataset / Transform 层（仅 ① 属性增强需要）。

### 现在不做的理由

1. **顺序不对**：应先确定"加哪种定向增强"，再选**载体**（见下方"载体订正"）。
2. **收益尚未被证明**：两条都还是假设，需先做小规模前置实验（如"小脸放大裁剪"跑 10 epoch
   对比 <32px 召回）。
3. **瓶颈可能在分辨率侧**：<32px 的脸在 640 输入下不足 10px，提高分辨率可能是成本更低的同方向解法。
4. **风险**：会改变训练数据分布，使既有 `best_model_v2.pt` 失去可比性；且 56 个测试
   **不覆盖训练数据路径**。

**若将来启动：第一步不是改 `augment.py`，而是补训练数据路径的测试**（自定义 Dataset 的变换
正确性、框与图同步性），否则改错不会有人发现。

### 结果

`src/data/augment.py` 头部写入定位说明；README、`docs/架构说明.md`、
`docs/项目现状与差距.md` 第八节与 CHANGELOG 同步。

### 载体订正（查证 ultralytics 8.4.75 源码后）

原先的"Albumentations vs ultralytics 自定义 Dataset"二分是**错的** —— `Albumentations` 是库，不是载体。真实载体：

| 载体 | 是什么 | 成本 |
|:---|:---|:---|
| **A. `augmentations` 超参钩子** | `v8_transforms()` 已内插 `Albumentations(transforms=hyp.augmentations)`，位于 **Mosaic/affine/MixUp 之后、RandomHSV/RandomFlip 之前**；`model.train(augmentations=[...])` 即可 | **一行配置** |
| **B. 自定义 Dataset** | 写代码接管数据构建 | 数天级 |

载体 A **会自动同步标注框**（几何变换时把 instances 转归一化 xywh 传入并写回）。
⚠️ 但 `contains_spatial` 靠**硬编码类名白名单**判断 —— **自定义变换类名不在表内会被当作纯像素变换，
导致框静默不同步、标注被破坏**。

**两条定向增强的载体归属**：① 属性感知增强 → **必须走 B**（标注属性进不了钩子的
`image + bboxes + class_labels` 通道，且需先补 G14 的属性解析）；
② 小脸放大裁剪 → **可走 A**（用白名单内的 `BBoxSafeRandomCrop` + `LongestMaxSize`，无需自定义类）。

**推进顺序因此改为**：先用载体 A 零代码验证 ② 是否真能提升小脸召回，有效再投入 ① 的 Dataset 级改造。

### 背景

项目文档长期同时宣称"ONNX FP16，6.17 MB"与"精度损失 < 1e-4"，而代码里写的是 `half=False`。
两者能否共存？最终出货哪个配置？此前无法回答，因为精度验证会因清单文件缺失而静默跳过。

### 实测（全部 3,226 张验证图，同一组权重）

| 变体 | mAP50 | mAP50-95 | P | R | ms | FPS | 体积 |
|:---|---:|---:|---:|---:|---:|---:|---:|
| PyTorch `.pt` | 0.66404 | 0.35618 | 0.8479 | 0.5937 | 11.4 | 87.8 | 5.95 MiB |
| ONNX FP32 | 0.66379 | 0.35670 | 0.8446 | 0.5959 | 27.7 | 36.1 | 11.70 MiB |
| ONNX FP16 | 0.66382 | 0.35627 | 0.8448 | 0.5959 | 27.9 | 35.8 | 5.88 MiB |

### 决策 1：出货 FP16，并把验收判据从张量 MAE 改为 mAP

| 候选 | 优点 | 缺点 | 结论 |
|:---|:---|:---|:---|
| FP32 | 张量误差 1.5e-5 | 11.70 MiB，超出 ≤10 MB 目标；CPU 吞吐与 FP16 相同 | 未选 |
| **FP16** | **5.88 MiB；mAP 与 PyTorch 无差别（−0.0002 / +0.0001）** | 需要更换判据 | **选定** |

**理由**：原判据"逐元素 MAE < 1e-4"**在数学上对 FP16 不可能通过**。模型输出是 `(1,5,8400)`
的候选框张量，一个坐标从 `320.12345` 舍入到 `320.1` 就贡献约 2e-2 —— 阈值的**两百倍** ——
而检测结果并没有改变。该指标衡量的是**浮点表示**，不是**模型行为**。

这正是当初有人把 `half=False` 打开的动机：用**体积翻倍**的代价，换取一个**与应用效果无关**的
数值一致性，同时让文档陷入自相矛盾。**该换的是判据，不是精度。**

### 决策 2：容差按精度区分，并如实报告跳过

`MAE_TOLERANCE = {True: 1e-1, False: 1e-4}`。同时把"缺 `val_list.txt` 时 `return True`（判定通过）"
改为返回 `None`，由 `main()` 明确报告 `[SKIPPED]`：**未测量不是通过**。

### 附带结论

- 三个变体的 mAP 差异都在噪声范围内 → **量化本身没有损害模型**。
- 本机 `onnxruntime` 无 CUDA provider，ONNX 只能跑 CPU：**PyTorch/CUDA 比 ONNX 快 2.4–3.3 倍**。
  可见 ONNX 在本机的价值是**可移植性**而非速度。追求速度应使用 `.pt`。
- 桥接当前默认加载 `.onnx`，即**跑在 CPU 上、GPU 闲置**。
  **是否把桥接默认模型改为 `.pt` —— 待决策，本次未改动。**

### 顺带推翻的一个此前结论

早前判定"v2 微调是负收益，三项全降"。重新在**保存下来的 best 权重**上测量后：
mAP50 0.66501→0.66404（−0.001），mAP50-95 0.35545→**0.35618**（+0.0007）。**实际是持平。**
此前依据的是 `results.csv` 末行，那是**最后一个 epoch**，与 best 权重不是同一组参数。
教训：**引用指标时必须写清是哪一组权重、哪个口径。**
