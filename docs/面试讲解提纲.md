## 三、项目定位与架构（怎么讲）

**不要说"外六内一""六人分工""课程设计"** —— 这是个人独立项目，就直说独立完成。
独立完成全链路在候选人中是加分项，包装反而减分。

### 一句话架构

> "整个仓库按**职责**分成五层：`src/paths.py` 提供全项目唯一的路径来源；`src/data/` 是数据管线；
> `src/train/` 训练；`src/eval/` 评估；`src/deploy/` 部署。`apps/vtube_bridge/` 是独立应用。
> 依赖严格单向：`deploy → eval → train → data → paths`。"

### 值得主动讲的三个设计原则

1. **代码 / 数据 / 产出三者分离** —— `src/`、`data/`、`artifacts/` 互不混放，因为三者生命周期不同。
2. **路径只有一处定义** —— 项目早期每个脚本用 `dirname(dirname(__file__))` 求项目根，扁平目录下没问题；
   一旦脚本进入子包（如 `src/deploy/detect.py`），同一个表达式会算出 `src/` 而不是项目根，所有路径同时失效。
   我把根目录解析收敛到 `src/paths.py` 一处，脚本从此可以自由移动。**这是我在重构时踩到并解决的真实问题。**
3. **脚本以 `python -m src.<pkg>.<module>` 运行** —— 导入关系显式，工作目录固定为项目根。

## 四、指标怎么讲（**重点段**）

### 4.1 精度

| 指标 | v1（100 epoch） | v2（+30 epoch） |
|:---|---:|---:|
| mAP50 | 0.663 | 0.662 |
| Precision | 0.849 | 0.846 |
| Recall | 0.595 | 0.595 |

> **必须主动说明口径**："这组数字是**全部 3,226 张验证图**上按 COCO 方式算的 AP50，
> 分母包含大量极小尺寸人脸。WIDER 官方榜单用的是 Easy/Medium/Hard **子集**的 VOC AP，
> **两者不可比**，所以我不会说自己达到了某个榜单分数。分项评估我还没做完，这是我要补的。"

> **v2 是负收益，如实说**："v2 是负收益 —— 0.663 降到 0.662，P 和 R 也各降了一点。
> 原因是它只在已收敛点附近做了 30 epoch 低学习率微调，训练数据分布没变。
> 真正的闭环需要把困难样本回流改变分布，这一步我没做到。"

### 4.2 速度与体积

| 项 | 实测 |
|:---|---:|
| PyTorch 网络前向 | 145 – 147 FPS（6.9 ms） |
| ONNX Runtime 前向 | 44 – 45 FPS（22.3 ms） |
| 模型体积 | `.pt` 5.95 MB / `.onnx` 5.88 MB |

> **必须主动说明口径**："这几个 FPS 是**裸网络前向**，调的是 `model.model(dummy)`，
> **不含** letterbox、解码和 NMS，也不是端到端帧率。而且 —— **ONNX 比 PyTorch 慢约 3 倍，
> 这不正常**，说明 ONNX 会话很可能没跑在 GPU 上；我的 benchmark 脚本同时注册了 CUDA 和 CPU
> 两个 ExecutionProvider 却没打印实际生效的是哪个，这一项我要先修脚本再重测。"

**这一段的杀伤力**：主动指出自己数字的边界和异常，比报一个漂亮的 FPS 更能建立信任。
面试官见过太多把前向速度说成端到端帧率的人。

## 五、核心亮点：VTube Studio 实时表情驱动

```
摄像头帧 640×480
   │
   ▼ ① YOLOv8n-face 检测人脸框                                  ~6 ms
   ▼ ② FaceBoxFilter   EMA(α=0.55) + 中值滤波(window=5)
   │                   + hold 3 帧（短暂丢失沿用上一框）
   │                   + reset_distance 判定新目标（切换人脸不滑动）
   ▼ ③ 裁剪 ROI（外扩 1.45 倍）                      ★ 核心设计：先检测再裁剪
   ▼ ④ MediaPipe FaceLandmarker                                 ~8 ms
   │      478 关键点 + 52 ARKit blendshape
   │      + facial transformation matrix → SVD 分解 → 头部欧拉角
   │      + 虹膜关键点归一化 → 视线方向 (-1, 1)
   ▼ ⑤ ParameterFilter  表情(α=0.45) / 头部(0.35) / 眼球(0.35) 三通道独立 EMA
   ▼ ⑥ TrackingCalibrationManager  按 VTS 返回的 min/max 裁剪
   │                                + 源范围自动采集映射 + 一键回中 + JSON 持久化
   ▼ ⑦ VTubeStudioWorker  daemon 后台线程，30 FPS 注入，断线 10 s 自动重连
VTube Studio → Live2D 形象跟随表情
   （旁路：PyQt5 调试窗口显示 16 个参数 / 摄像头预览 / 点击选脸）
```

### 最该讲的一句：为什么"先检测再裁剪"

> "VTS 自带的跟踪是把整张 640×480 画面直接送给内部模型，人脸可能只占画面的六分之一。
> 我先用自己训练的 YOLO 精确定位人脸框，**外扩 1.45 倍后裁剪**，再送 MediaPipe。
> 人脸在输入中的占比大幅提升，478 个关键点的定位和表情系数都更准，同时排除了背景干扰。
> 1.45 这个比例是权衡出来的：裁太紧会切掉下巴和额头、导致姿态估计不稳，裁太松背景干扰就回来了。"

### 工程细节（体现"真的跑过摄像头"）

| 组件 | 解决的问题 |
|:---|:---|
| **FaceBoxFilter** | 三层防护：EMA 抑制抖动 + 中值滤波抗单帧跳变 + hold 帧避免短暂丢失时闪烁；`reset_distance` 保证切换人脸时不从旧位置滑过去 |
| **ParameterFilter** | 表情/头部/眼球**三通道独立**平滑 —— 表情要快，头部和眼球过快点会让人偶显得神经质 |
| **VTubeStudioWorker** | WebSocket 发送放在 daemon 线程，**网络 I/O 不阻塞推理主循环**；断线 10 秒重连，期间检测照常 |
| **TrackingCalibrationManager** | 读取 VTS 返回的同名参数 min/max 做裁剪；自动采集源端范围映射到目标区间；支持一键回中 |
| **QtDebugWindow** | 16 个参数实时显示 + 校准交互 + 点击选脸 |

### 诚实回答"这是不是拼装"

> "关键点提取用的是 Google 官方模型，我没有重训，这点我不回避。
> 我的工作在**管线编排与时序工程** —— 检测前置裁剪、多级滤波、范围校准、线程解耦。
> 这些是把两个现成模块变成一个能长时间稳定运行的东西所必需的部分。"

## 六、关键技术决策（一句话一个）

| 决策 | 理由 |
|:---|:---|
| 检测框架选 YOLOv8n | 3.0M 参数、5.95 MB，单卡可训，实时性有富余；人脸检测是单类密集小目标任务，更大模型在 640 分辨率下小脸收益有限 |
| `nc=1` 单类 | 只检人脸，head 输出通道降到 4+1，参数与推理开销都更小 |
| ONNX 静态导出（`dynamic=False` + `simplify`） | 部署固定 640×640，静态图能让运行时做更充分的图优化 |
| 导出后做精度回归验证 | 逐样本比对 PyTorch 与 ONNX 输出的 MAE，阈值 1e-4，失败就 `exit(1)`；**这是我认为最该做的一步** |
| 计时前后 `torch.cuda.synchronize()` | CUDA 内核异步执行，不同步会把耗时测成接近 0 |
| 桥接保持独立应用（`apps/`） | 自带 MediaPipe 模型与 GUI，耦合低、可单独交付 |

### 关于指标

| **mAP 0.664 高吗？** | "坦白说这个口径下不算高。它是全验证集 COCO 式 AP50，分母包含大量 <16px 的极小脸。WIDER 榜单用的是 Hard 子集的 VOC AP，口径不同不能比。我目前**没有** Hard 子集的分项结果，这是评估体系最大的缺口。" |

| **v2 微调提升多少？** | "**负数**。0.663 → 0.662，P 和 R 也各降一点。它只是在收敛点附近做了 30 epoch 低学习率微调，数据分布没变。真正的闭环要困难样本回流，我没做。" |
| **FPS 多少？** | "网络前向 145–147 FPS，但**这不含 letterbox 和 NMS，不是端到端**。而且 ONNX 反而比 PyTorch 慢 3 倍，说明 ONNX 会话可能没跑在 GPU 上 —— 我的 benchmark 没打印实际生效的 ExecutionProvider，这是个待修的缺陷。" |
| **mAP50-95 只有 0.354？** | "说明定位精度是短板。高 IoU 阈值下小框回归误差被放大 —— 十几像素的脸偏 1–2 像素，IoU 就跌破 0.75。" |

### 关于模型与训练

| 可能被问 | 建议回答 |
|:---|:---|
| **为什么选 YOLOv8n？** | 3M 参数、6MB，单卡可训，实时性富余；单类小目标任务不需要更大容量。 |
| **训练超参？** | 以 `args.yaml` 为准：batch=8、imgsz=640、AdamW、lr 1e-3→1e-5 余弦退火、amp=true、mosaic=1.0（v2 降到 0.5）、workers=2、seed=0、deterministic=true、close_mosaic=10。 |
| **`nbs=64` 是什么？** | nominal batch size，用于损失归一化。实际 batch(8) < nbs(64) 时 ultralytics 会按比例缩放 loss，等效于梯度累积 8 步。**注意**：设计文档写的"`accumulation_steps=2` 模拟 batch=32"并未实现，`train.py` 里没有这个参数。 |
| **数据增强？** | 训练用的是 ultralytics **内置**增强（Mosaic/HSV/翻转/缩放）。另外我写了一个 Albumentations 管线做增强效果可视化，**但没有把它接进训练** —— 这是个未完成的解耦点，我不掩饰。 |
| **自采数据呢？** | 设计文档承诺 500 张侧脸/遮挡/暗光，**我没做**，最终只用 WIDER 公开集。这也是 Recall 偏低的原因之一。 |
| **显存够吗？** | 机型是 3060 Laptop **6 GB**。`batch=8 + 640` 会超额分配 —— 日志峰值 11.1 GB，Windows 溢出到共享内存，吞吐从 5.8 it/s 掉到 1.7。降到 batch=4 或 imgsz=512 是明确的优化方向。 |
| **训练中遇到什么问题？** | 最好的一个故事，三段式：① 早期 val 指标全为 0（`results.csv` 首行 `val/box_loss=0`），我先用 `val=False` 让训练跑起来；② 定位到 val split 数据缺失，重下 3,226 张；③ 用 `resume=True` 从 `last.pt` **断点续训**补到 100 epoch。另外 **Windows 中文路径下 `cv2.imread` 会静默返回 `None`**，我用 `imdecode` 写了兜底补丁。 |
